# 要件定義自動生成Bot 要件定義書

作成日: 2026-07-10
バージョン: v0.1（初版）

---

## 1. 背景・目的

### 1.1 背景
Discord経由でAIに作業（コード生成・実行など）を自動で任せるシステムを構築したいという構想がある。
しかし、いきなり実装に着手するのではなく、まず「人間が作りたいシステムの要望（ざっくりしたもの）を伝えると、AIが対話を通じて要件定義書を作成してくれる仕組み」を第一段階として構築する。

### 1.2 目的
- 人間が口頭・簡潔に伝えたシステムの要望を、AI同士の議論を通じて具体化し、実装可能なレベルの要件定義書に落とし込む。
- 人間は都度すべてを言語化する負担を減らし、要所でのYes/No・修正指示のみで要件定義を完成させられるようにする。
- 本Botで得られた要件定義書を土台に、将来的にはコード生成・実行を自動で行うAIシステム（本構想の第二段階）へと展開する。

### 1.3 スコープ（本要件定義の対象）
本要件定義書がカバーするのは **「要件定義書を自動生成する仕組み（Bot）」** のみであり、その後の「コード自動生成・実行システム」は対象外（将来フェーズ）とする。

---

## 2. システム概要

Discord上の特定チャンネルに、人間が実装したいシステムの概要をラフに投稿すると、裏側で3つの役割を持つAI（Ollama上で動作する別々のモデル）が議論を行い、要件定義書を練り上げる。議論の節目ごとに人間へ確認を取り、最終的に本格的な要件定義書（Markdown）をローカルファイルとして出力する。

### 2.1 登場する3つのAIロール

| ロール | 役割概要 |
|---|---|
| 指示役AI | 人間の要望を解釈し、要件定義役への指示・論点整理を行う進行役 |
| 要件定義役AI | 指示役からの情報をもとに要件定義書のドラフトを作成・更新する |
| レビュー役AI | 要件定義役が作成したドラフトをレビューし、不備・矛盾・不足点を指摘する（OK/NG判定を行う） |

3つのロールはそれぞれ異なるOllamaモデルを使用する（役割ごとにモデルを使い分け、.envで設定可能とする）。

---

## 3. 全体フロー

1. 管理者がDiscordの特定チャンネルに、作りたいシステムの概要をラフに投稿する。
2. Botがトリガーを検知し、セッションを開始する（DBに記録）。
3. 裏側で「指示役 → 要件定義役 → レビュー役」の順に議論のラウンドを実行する。
   - レビュー役がNG（要修正）と判断した場合、指摘事項を要件定義役にフィードバックし、ドラフトを更新する。
4. 一定の節目（例: ドラフトが一区切りついたタイミング）で、Botが人間にドラフト内容を提示し、確認を求める。
5. 人間はテキスト返信で「OK」または「修正指示」を送る。
   - 「修正指示」の場合、その内容を反映して2〜3のラウンドを再度実行する。
   - 「OK」の場合、次の論点に進むか、要件定義書を確定する。
6. 以下いずれかの条件で確定・終了する。
   - レビュー役AIがOKと判定した場合（早期確定）
   - ラウンド数が`.env`で設定した上限に達した場合
7. 確定した要件定義書をMarkdownとしてローカルに保存する（Gitへのcommitは人間が手動で行う）。

## 4. 機能要件

| ID | 要件 |
|---|---|
| F-01 | Discordの特定チャンネルへの投稿をトリガーとしてセッションを開始できること |
| F-02 | 指示役・要件定義役・レビュー役の3つのAIロールが、それぞれ異なるOllamaモデルを使って動作すること |
| F-03 | 3AI間の議論は、デフォルトではDiscord上には表示せず裏側（サーバー内部）で完結すること。ただし`.env`の設定により、全ての発言をDiscordに投稿する「可視化モード」に切り替えられること |
| F-04 | 議論の節目で、現在のドラフト状況を人間にDiscord上で提示し、確認（OK/修正指示）を求めること |
| F-05 | 人間はテキスト返信で「OK」または「修正指示」を送ることで対話を継続できること |
| F-06 | 修正指示に応じてAI同士が再度議論し、ドラフトを更新できること |
| F-07 | レビュー役AIがOKと判定した場合、それ以降のラウンドを待たずに要件定義を確定できること |
| F-08 | ラウンド数の上限に達した場合、自動的にその時点の内容で要件定義を確定すること |
| F-09 | ラウンド数の上限は`.env`ファイルで設定変更可能であること |
| F-10 | 確定した要件定義書を、背景・目的、機能要件、非機能要件等を含む本格的なテンプレート形式のMarkdownファイルとして生成すること |
| F-11 | 生成したMarkdownファイルはサーバーのローカルファイルシステムに保存すること（Gitコミットは対象外） |
| F-12 | 進行中の対話履歴（セッション状態）をSQLite等のDBに保存し、Bot再起動後も再開・参照できること |
| F-13 | 同時に進行できるセッションは1つのみとする（新規セッション開始時、進行中セッションがあればその旨を通知する） |
| F-14 | 本Botの利用は管理者（自分）のみに制限すること |
| F-15 | 要件定義役AIまたはレビュー役AIがドラフトに関して不明点を持った場合、通常のOK/NG判定フローを待たず、質問として人間に確認を求められること |
| F-16 | 質問対応にかかったやり取りは、ラウンド数の上限（MAX_ROUNDS）にはカウントしないこと |
| F-17 | 「質問への確認」と「通常のドラフト確認（OK/修正指示）」は、Discord上で見た目上区別できること（例: 質問は❓、ドラフト確認は📝） |
| F-18 | 人間が質問に回答した後、同じ論点について再度質問が生じた場合、即座に人間へ戻さず、AI同士（要件定義役・レビュー役・指示役）で解決を試みる「内部協議」を挟むこと |
| F-19 | 内部協議の最大試行回数は`.env`ファイルで設定変更可能であること。試行回数を超えてもなお解決しない場合は、改めて人間に質問すること |
| F-20 | `.env`の設定（例: `SHOW_AI_DISCUSSION`）により、指示役・要件定義役・レビュー役の発言（内部協議中の発言も含む）を、発生の都度リアルタイムでDiscordに投稿できること。デフォルトはOFFとする |

## 5. 非機能要件

| ID | 要件 |
|---|---|
| N-01 | Discord Botの実装言語はNode.js（discord.js等）とすること |
| N-02 | AIモデルの推論はOllama経由で行い、Botサーバーとは別のGPUマシン上のOllamaサーバーにHTTP経由でアクセスすること |
| N-03 | Ollamaの接続先（ホスト・ポート）、各ロールに使用するモデル名、ラウンド数上限などの可変パラメータは`.env`で管理すること |
| N-04 | 対話履歴・セッション状態はSQLite等の軽量DBで管理し、永続化すること |
| N-05 | Ollamaサーバーへの接続に失敗した場合やタイムアウトが発生した場合、エラーをDiscord上に通知し、セッションを中断せず再試行またはユーザーに状況を伝えられること（詳細な挙動は今後要検討） |
| N-06 | 本Botは管理者以外からのメッセージ・コマンドを無視すること（認可されていないユーザーからの操作を防止） |
| N-07 | Discordの1メッセージ文字数制限（2000文字）を超える投稿が発生する場合、短い発言（指示・レビューコメント・質問等）は自動分割送信し、要件定義役のドラフト全文のような長文はMarkdownファイルとして添付投稿すること |

## 6. 想定環境変数（.env）例

```
# Discord
DISCORD_BOT_TOKEN=
DISCORD_TARGET_CHANNEL_ID=
DISCORD_ADMIN_USER_ID=

# Ollama接続先
OLLAMA_HOST=http://<GPUサーバーIP>:11434

# 役割ごとのモデル
OLLAMA_MODEL_DIRECTOR=      # 指示役
OLLAMA_MODEL_REQUIREMENTS=  # 要件定義役
OLLAMA_MODEL_REVIEWER=      # レビュー役

# ループ制御
MAX_ROUNDS=5
MAX_INTERNAL_DELIBERATION=1   # 質問への回答後、再度質問が出た場合にAI同士で解決を試みる最大回数

# 可視化モード
SHOW_AI_DISCUSSION=false   # trueにすると3AIの発言をリアルタイムでDiscordに投稿する

# 出力先
OUTPUT_DIR=./output/requirements
```

## 7. 技術スタック（暫定）

- 言語: Node.js（discord.js）
- AI推論基盤: Ollama（別GPUマシン上でホスト、役割ごとに異なるモデル）
- データ永続化: SQLite
- 出力形式: Markdown（ローカルファイル保存）

## 9. 将来構想（参考・本フェーズ対象外）

本Botで生成された要件定義書をインプットとして、将来的には以下のフェーズを段階的に構築していく構想がある（いずれも本要件定義の対象外）。

### 9.1 フェーズ2: システム設計自動生成の仕組み
フェーズ1（本Bot）で確定した要件定義書（Markdown）をインプットとして、AIが自動でシステム設計（UI設計・DB設計・詳細設計等）を行う仕組みを構築する。
- フェーズ1と同様に「指示役・設計役・レビュー役」のような3AI協調構成を踏襲する想定。
- 節目ごとの人間確認、ラウンド上限、DB永続化、Markdown出力といった設計パターンもフェーズ1を雛形として流用する想定。
- フェーズ1の運用実績（節目の区切り方、AIの役割分担の勘所など）を踏まえてから、詳細要件を定義する。
- 入力: フェーズ1で出力された要件定義書（Markdown）
- 出力: システム設計書（UI設計・DB設計・詳細設計を含むMarkdown、想定）

### 9.2 フェーズ3: コード自動生成・実行システム
フェーズ2で確定したシステム設計書をインプットとして、以下を実現する構想がある。

- Discordから指示を受け、Dockerサンドボックス環境上でAIがコードを生成・実行する
- 単発のコード実行だけでなく、既存Gitリポジトリの操作（クローン・push等）にも対応する
- 重要な操作の前には人間の承認フローを設ける（詳細未定）

### 9.3 フェーズ間の連携方針（メモ）
- 各フェーズはMarkdownファイルを介して疎結合に連携させる想定（前フェーズの出力ファイルを次フェーズの入力とする）。
- 一気に全フェーズを設計するのではなく、フェーズ1を実際に運用してから、その知見をもとにフェーズ2以降を順次要件定義していく方針とする。
